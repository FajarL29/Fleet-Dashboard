# Authentication Backend Analysis

**Status:** Updated after minimum authentication hardening implementation.

**Repository:** CapabilityCenter-Telematics-BE  
**API base:** `http://localhost:3000/api/v1`

## Executive Summary

The backend does contain a functional login flow in source and it is registered in Express:

- `POST /api/v1/auth/login`
- `POST /api/v1/auth/register`
- `POST /api/v1/auth/refresh`

Access and refresh JWTs are generated by this backend with `jsonwebtoken`. Access tokens expire after one hour and refresh tokens after seven days. Refresh tokens are stored in `tb_m_users.refreshToken`.

The validation middleware has been hardened so every route that attaches `verifyToken` requires `Authorization: Bearer <JWT>`; validation no longer depends on `x-device: MOBILE`. There is now a registered logout route. There is still no dedicated profile or `/me` route and no role/permission enforcement.

Passwords are stored using reversible AES encryption through `CryptoJS`, not a one-way password hash. The login response returns the complete database user row, so it may expose stored credential and refresh-token fields to the client.

## Current JWT Flow

### Token generation

`middleware/auth.js` imports `jsonwebtoken` and exports:

- `generateToken(payload)`: signs an access token with `process.env.SECRET_KEY` and `{ expiresIn: "1h" }`.
- `generateRefreshToken(user)`: signs a refresh token with the same secret and `{ expiresIn: "7d" }`, then stores it in `tb_m_users.refreshToken`.

The access-token payload assembled by `generateToken` is:

```json
{
  "user_id": "payload.id ?? payload.user_id",
  "username": "payload.username",
  "fullname": "payload.fullname",
  "email": "payload.email",
  "created_by": "payload.created_by",
  "created_dt": "payload.created_dt",
  "address": "payload.address"
}
```

The refresh-token payload is:

```json
{
  "userId": "user.id ?? user.user_id",
  "username": "user.username"
}
```

No issuer or audience is supplied. The signing secret is read from the environment as `SECRET_KEY`; its value is intentionally not reproduced here. The same environment secret is also used by `helpers/security.js` for AES password encryption.

The login controller passes the result of `SELECT * FROM tb_m_users ...` directly to `generateToken` and `generateRefreshToken`. `generateToken` reads `payload.id`, while the repository's documented primary key is `user_id`. Therefore the access-token `user_id` claim can be undefined unless the live database result provides an `id` field by some other mechanism. The refresh-token generator explicitly supports both `id` and `user_id`.

### Token validation

`middleware/auth.js`, function `verifyToken`, performs the following:

1. Requires `authorization` in the `Authorization: Bearer <JWT>` form.
2. Calls `jwt.verify(token, process.env.SECRET_KEY)`.
3. Looks up the user by the decoded `username` in `tb_m_users`.
4. Stores the database row in `req.user`, decoded claims in `req.auth`, and calls `next()`.

Validation does not explicitly check the scheme is `Bearer`; it only takes `authorization.split(" ")[1]`. The decoded claims are not used as the final user object; the user is reloaded from MySQL by username.

Error behavior:

| Condition | Response |
| --- | --- |
| Authorization header missing | HTTP 401, `No token provide` |
| Authorization scheme/token missing | HTTP 401, `No token provide` |
| Invalid JWT/signature | HTTP 401, `Token is invalid` |
| Expired JWT | HTTP 401, `Token has expired` |
| Valid JWT but no matching username | HTTP 401, `User not found` |

The shared unauthorized envelope is defined in `helpers/response.js`:

```json
{
  "stat_code": 401,
  "status": "Your username / password wrong",
  "message": "..."
}
```

### Protected route groups

Routes that attach `verifyToken` include:

- `/users`
- `/user-vehicle/informations` and `/user-vehicle/connect`
- `/safety/get/:vehicle_id`
- vehicle registry routes and selected service-history routes
- `/geofencing`
- `/trip`
- `/trip_history`
- `/camera`
- `/drowsiness`
- `/pothole/getall`

These routes now require a valid Bearer JWT whenever `verifyToken` is attached. The `x-device` header is no longer required and is ignored by the JWT middleware. Several ingestion and auxiliary routes remain explicitly open, including vehicle status ingestion, pothole event ingestion, and drowsiness event ingestion (`POST /api/v1/drowsiness/`).

## User Master: `tb_m_users`

The table name is defined in `config/tables.js`. The repository reads and writes it through raw query helpers rather than a model or ORM repository.

Evidence-supported fields:

| Field | Evidence and usage |
| --- | --- |
| `user_id` | Documented primary key; used by refresh-token persistence and vehicle/user relationships |
| `username` | Login lookup, JWT claim, middleware lookup, user-vehicle filtering |
| `fullname` | Included in the access-token payload |
| `email` | Included in the access-token payload |
| `password` | Read during login and written during registration/user creation |
| `refreshToken` | Written, read, and cleared by refresh-token helpers |
| `created_by` | Included in the access-token payload and accepted in user writes |
| `created_dt` | Included in the access-token payload and documented as an audit field |
| `address` | Included in the access-token payload and documented as optional metadata |

The repository's documentation also mentions `updated_dt` as a general audit field, but authentication code does not use it. No `role`, permission, employee-ID, or account-status field is established by the authentication source inspected here. A live database inspection would be required to confirm any additional columns.

### Credential storage

`helpers/security.js` uses `CryptoJS.AES.encrypt(password, process.env.SECRET_KEY)` and `CryptoJS.AES.decrypt(...)`. `controllers/auth/auth.controllers.js` decrypts the stored value and compares the plaintext with `req.body.password`.

Therefore:

- a password credential exists;
- password transformation exists;
- it is reversible encryption, not bcrypt, Argon2, scrypt, or another one-way password hash;
- the comparison is an exact plaintext comparison after decryption.

## Login Capability

### Registered contract

**Method:** `POST`  
**Path:** `/api/v1/auth/login`  
**Registration:** `routes/auth/index.js`, mounted by `routes/index.js` and `app.js`

**Request body:**

```json
{
  "username": "string",
  "password": "string"
}
```

The controller queries `tb_m_users` by `username`, decrypts the first row's `password`, and compares it with the supplied password.

**Success response:** HTTP 200 using the common response envelope:

```json
{
  "status": "success",
  "stat_code": 200,
  "data": {
    "token": "<access JWT>",
    "refreshToken": "<refresh JWT>",
    "user": "<complete tb_m_users row>"
  }
}
```

The access-token field is named `token`, while the refresh endpoint uses `accessToken` for its newly issued access token. This inconsistency must be handled by the Flutter client or normalized in a future implementation.

**Wrong credentials:** HTTP 401 with message `Your username / password wrong`. Missing fields, no matching row, database errors, or decryption errors can instead reach the controller catch block and produce HTTP 500 through `response.error`.

### Registration

`POST /api/v1/auth/register` is registered and encrypts `req.body.password` before inserting the request body into `tb_m_users`. It is protected only by `preventSqlInjection`, not JWT middleware.

## Refresh Token

Refresh-token support exists and is registered.

**Method:** `POST`  
**Path:** `/api/v1/auth/refresh`  
**Request body:**

```json
{
  "refreshToken": "<refresh JWT>"
}
```

The controller verifies the JWT, loads the stored token by decoded `userId`, requires an exact match with `tb_m_users.refreshToken`, reloads the user, issues a new access token and rotates the refresh token.

**Success response:** HTTP 200:

```json
{
  "status": "success",
  "stat_code": 200,
  "data": {
    "accessToken": "<new access JWT>",
    "refreshToken": "<new refresh JWT>"
  }
}
```

Missing, invalid, expired, or non-matching refresh tokens return HTTP 401 with `Invalid or expired refresh token` (or `Refresh token is required` when absent).

## Logout and Revocation

`POST /api/v1/auth/logout` is now registered behind `verifyToken`. It resolves `req.user.user_id` (with legacy `id` fallback) and clears `tb_m_users.refreshToken` through a parameterized `UPDATE ... SET refreshToken = NULL` query.

There is no access-token blacklist or server-side access-token revocation. Logout invalidates the stored refresh token; the current access JWT remains valid until its one-hour expiry. Flutter must also delete both locally stored tokens.

## Session Validation and Profile

No `/me` or `/profile` endpoint was found. `GET /api/v1/users/get?username=...` exists and is protected by `verifyToken`, but it requires a username query parameter and returns a user lookup rather than a session/profile contract.

The access token contains identity claims such as `username`, `fullname`, `email`, and `user_id` (subject to the `payload.id` issue described above). However, backend middleware performs an additional database lookup by username, so the backend does not treat the JWT alone as the complete current user record. The Flutter client can restore a basic identity from claims, but there is no dedicated server profile endpoint for authoritative session restoration.

## Hardcoded Frontend Token

The backend can legitimately recreate a token only by using a valid `tb_m_users` row with the backend's `SECRET_KEY`, through the registered login flow or token-generation functions. The previous frontend hardcoded JWT therefore appears intended to represent a backend user identity accepted by `verifyToken`, especially its `username` claim, and to be used with `x-device: MOBILE` plus an `Authorization` header.

The repository does not provide evidence that the hardcoded token came from an external identity provider. Do not reproduce or decode any token or secret in client code. Existing environment credentials should also be treated as sensitive and rotated outside this analysis.

## Implemented Minimum Hardening

For the requested MVP, the smallest usable flow is:

```text
Flutter credentials
  -> POST /api/v1/auth/login
  -> receive access token and user identity
  -> send Authorization: Bearer <token> to fleet APIs
  -> delete local tokens on logout
```

The minimum backend work has been implemented as follows:

1. Login validates required credentials and missing users without attempting to decrypt an absent value.
2. Login returns an allowlisted user projection; `password` and `refreshToken` are excluded.
3. Access-token generation uses `payload.id ?? payload.user_id` for the canonical user ID claim.
4. Protected routes consistently require `Authorization: Bearer <JWT>` without a device-header bypass.
5. Logout is registered and clears the stored refresh token with a parameterized NULL update.
6. Flutter still deletes access and refresh tokens locally on logout.

This does not require OAuth, SSO, Keycloak, a new RBAC system, or a new refresh-token design. The existing refresh flow can remain optional for the first Flutter login milestone.

## Files That Would Need Modification If Approved

Implemented runtime surface:

- `controllers/auth/auth.controllers.js`: input handling, safe response projection, ID mapping, and optional logout behavior.
- `middleware/auth.js`: consistent Bearer validation, device-header policy, and canonical user ID handling.
- `routes/auth/index.js`: register logout if server-side refresh invalidation is selected.
- `helpers/security.js`: unchanged; reversible password encryption remains a documented security debt for compatibility.
- `docs/api-documentation.md` and `swagger.json`: document the actual login, refresh, logout, and security contract.

Database migration changes are not specified because the repository does not contain a `tb_m_users` creation migration. The live schema must be inspected before proposing column changes.
